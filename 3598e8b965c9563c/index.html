The simply typed λ-calculus

Each piece of math is followed by its Rocq code from Discussion 6/Discussion6.v, in file order.

1. Expressions

\[ \begin{aligned} \tau &::= \mathsf{int} \mid \mathsf{bool} \mid \tau_1 \to \tau_2 \\ e &::= n \mid \mathsf{true} \mid \mathsf{false} \mid x \mid \lambda \class{hl-new}{\bbox[yellow,1pt]{x{:}\tau}}.\, e \mid e_1\, e_2 \\ &\quad\mid e_1 + e_2 \mid \mathsf{if}\ e\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2 \end{aligned} \]

Here \(n\) ranges over integers and \(x\) over variable names. The highlighted \(\class{hl-new}{\bbox[yellow,1pt]{x{:}\tau}}\) is what's new compared to the untyped λ-calculus: a \(\lambda\) says what type its argument has, so expressions mention types. That is all types are used for so far.

In Rocq each form is one constructor of exp. The language's symbols differ from Rocq's own, so they can't be confused: ⊕ is \(+\), TRUE/FALSE are \(\mathsf{true}\)/\(\mathsf{false}\), INT/BOOL/⇒ are the types, and e1 · e2 is application.

Examples

\[ \begin{aligned} &1 + 2 \\ &\lambda x{:}\mathsf{int}.\, x + 1 &&\text{adds one} \\ &(\lambda x{:}\mathsf{int}.\, x + 1)\, 2 &&\text{applied to } 2 \\ &\lambda f{:}\mathsf{int} \to \mathsf{int}.\, \lambda x{:}\mathsf{int}.\, f\,(f\, x) &&\text{applies } f \text{ twice} \end{aligned} \]

The grammar also allows expressions that make no sense, like \(\mathsf{true} + 1\). Ruling those out is what the type system is for.

2. Evaluation

Values

A value is a finished answer:

\[ v ::= n \mid \mathsf{true} \mid \mathsf{false} \mid \lambda x{:}\tau.\, e \]

A \(\lambda\) is a value whatever its body is: evaluation doesn't look inside it. In Rocq, value e says that \(e\) has one of these four forms.

Values are a subset of expressions. This is how Rocq represents a subset: for a type \(A\) and a property \(P\), the type \(\{ x : A \mid P\,x \}\) (a sigma type, or subset type) has the \(x\)'s in \(A\) with property \(P\). An element of it is a pair: an \(x\), together with a proof of \(P\,x\).

So the values, as a type, are val \(= \{ e : \mathsf{exp} \mid \mathsf{value}\ e \}\): an expression together with a proof that it is a value. exp_of v forgets the proof and gives back the expression.

Small-step rules

One step, \(e \longrightarrow e'\), is given by these nine rules. The highlighted four do the real work. The other five only say where to look next: the function, then the argument; the left summand, then the right one; the condition of an if.

\[\frac{}{(\lambda x{:}\tau.\, e)\, v \longrightarrow e[x \mapsto v]}\]
\[\frac{e_1 \longrightarrow e_1'}{e_1\, e_2 \longrightarrow e_1'\, e_2}\]
\[\frac{e_2 \longrightarrow e_2'}{v\, e_2 \longrightarrow v\, e_2'}\]
\[\frac{}{n_1 + n_2 \longrightarrow n_3}\ (n_3 = n_1 + n_2)\]
\[\frac{e_1 \longrightarrow e_1'}{e_1 + e_2 \longrightarrow e_1' + e_2}\]
\[\frac{e_2 \longrightarrow e_2'}{n + e_2 \longrightarrow n + e_2'}\]
\[\frac{e \longrightarrow e'}{\mathsf{if}\ e\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2 \longrightarrow \mathsf{if}\ e'\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2}\]
\[\frac{}{\mathsf{if}\ \mathsf{true}\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2 \longrightarrow e_1}\]
\[\frac{}{\mathsf{if}\ \mathsf{false}\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2 \longrightarrow e_2}\]

Redexes

So we will pull out the "real" reduction rules as their own step, written \(r \longrightarrow_{\mathsf{r}} r'\). The expression \(r\) on the left is a redex, short for reducible expression. In Rocq the relation is redex, written ⟶r.

\[(\lambda x{:}\tau.\, e)\, v \longrightarrow_{\mathsf{r}} e[x \mapsto v]\]
\[n_1 + n_2 \longrightarrow_{\mathsf{r}} n_3 \quad (n_3 = n_1 + n_2)\]
\[\mathsf{if}\ \mathsf{true}\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2 \longrightarrow_{\mathsf{r}} e_1\]
\[\mathsf{if}\ \mathsf{false}\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2 \longrightarrow_{\mathsf{r}} e_2\]

Evaluation contexts

The other five rules all say the same kind of thing: where in the expression to look for the next redex. We can abstract over that with the notion of an evaluation context (Felleisen and Hieb 1992): an expression with one hole \(\bullet\) in it, at the place where the next step happens.

\[ \begin{aligned} E ::= {} & \bullet \mid E\, e \mid v\, E \mid E + e \mid n + E \\ \mid {} & \mathsf{if}\ E\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2 \end{aligned} \]

\(E[e]\) is \(E\) with its hole filled by \(e\). Each form of \(E\) is one of the five rules: \(E\, e\) looks in the function first, and \(v\, E\) in the argument once the function is a value; \(E + e\) looks in the left summand, and \(n + E\) in the right one once the left is a number; \(\mathsf{if}\ E\ \cdots\) looks in the condition. There is no \(\lambda x{:}\tau.\, E\): evaluation never looks inside a \(\lambda\).

Some examples:

  • \((1 + 2) + 3 = E[1 + 2]\) with \(E = \bullet + 3\): the left summand comes first.
  • \(1 + (2 + 3) = E[2 + 3]\) with \(E = 1 + \bullet\): the left summand is already a number, so look on the right.
  • \((\lambda x{:}\mathsf{int}.\, x + 1)\, (1 + 1) = E[1 + 1]\) with \(E = (\lambda x{:}\mathsf{int}.\, x + 1)\, \bullet\): the function is a value, so look in the argument.
  • Not evaluation contexts: \((1 + 2) + \bullet\), because the left summand isn't a number yet, and \(\lambda x{:}\mathsf{int}.\, \bullet\), because evaluation doesn't look inside a \(\lambda\).

In Rocq, the \(v\) in \(v\, E\) is a val, so it is guaranteed to be a value.

Steps, with evaluation contexts

Now one rule does the job of all nine: take the redex out of its context, do the work, and put the result back.

\[\frac{r \longrightarrow_{\mathsf{r}} r'}{E[r] \longrightarrow E[r']}\]

With \(E = \bullet\) this is one of the four redex rules. Every other form of \(E\) is one of the five rules that only say where to look.

For example, \((1 + 2) + 3 \longrightarrow 3 + 3\), with \(E = \bullet + 3\) and the redex \(1 + 2 \longrightarrow_{\mathsf{r}} 3\).

A run. Each step is one use of the rule: choose \(E\); the redex is whatever fills its hole. This run uses both holes of an application: first the function (\(E\, e\)), then, once it is a value, the argument (\(v\, E\)).

\[ \begin{array}{lll} (\lambda x{:}\mathsf{int}.\, \lambda y{:}\mathsf{int}.\, x + y)\, 1\, (1 + 1) & & \\ \quad\longrightarrow (\lambda y{:}\mathsf{int}.\, 1 + y)\, (1 + 1) & \quad E = \bullet\, (1 + 1) & \text{left hole} \\ \quad\longrightarrow (\lambda y{:}\mathsf{int}.\, 1 + y)\, 2 & \quad E = (\lambda y{:}\mathsf{int}.\, 1 + y)\, \bullet & \text{right hole} \\ \quad\longrightarrow 1 + 2 & \quad E = \bullet & \\ \quad\longrightarrow 3 & \quad E = \bullet & \end{array} \]

In the second step the function is a value, so \(E\) looks in the argument. In Rocq the val in that \(E\) is the function together with the proof v_lam that it is a value.

Multi-step

\(e \longrightarrow^* e'\) means zero or more steps:

\[\frac{}{e \longrightarrow^* e}\ (\text{refl})\]
\[\frac{e_1 \longrightarrow e_2 \quad e_2 \longrightarrow^* e_3}{e_1 \longrightarrow^* e_3}\ (\text{step})\]

The run above is one multi-step: \((\lambda x{:}\mathsf{int}.\, \lambda y{:}\mathsf{int}.\, x + y)\, 1\, (1 + 1) \longrightarrow^* 3\), by its four steps and then (refl).

Stuck

For the example below, a one-off definition: an expression is stuck when it is not a value and cannot step, so evaluation hasn't finished, but no rule applies. In Rocq it lives in its own Section, as a Let that exists only until the section ends.

\[ \mathsf{stuck}(e) \;:\Longleftrightarrow\; e \text{ is not a value} \;\text{ and }\; \text{there is no } e' \text{ with } e \longrightarrow e' \]

A run that gets stuck:

\[ (\lambda x{:}\mathsf{int}.\, x + 1)\, \mathsf{true} \longrightarrow \mathsf{true} + 1, \qquad \mathsf{stuck}(\mathsf{true} + 1) \]

The β step doesn't look at the annotation \(x{:}\mathsf{int}\): evaluation never checks types. And \(\mathsf{true} + 1\) is stuck: it isn't a value, and however you write it as \(E[r]\), no redex rule adds a Boolean. Ruling out runs like this is the type system's job.

3. Typing

Contexts

A context lists the variables in scope with their types:

\[\Gamma ::= \cdot \mid \Gamma, x{:}\tau\]

\(x{:}\tau \in \Gamma\) means the rightmost \(x\) in \(\Gamma\) has type \(\tau\). So later bindings hide earlier ones, just as an inner \(\lambda x\) hides an outer one. In Rocq a context is a list, and \(\Gamma, x{:}\tau\) puts \(x{:}\tau\) at the front.

Typing rules

\(\Gamma \vdash e : \tau\) reads "in context \(\Gamma\), \(e\) has type \(\tau\)". There is one rule for each form of expression:

\[\frac{}{\Gamma \vdash n : \mathsf{int}}\]
\[\frac{}{\Gamma \vdash \mathsf{true} : \mathsf{bool}}\]
\[\frac{}{\Gamma \vdash \mathsf{false} : \mathsf{bool}}\]
\[\frac{x{:}\tau \in \Gamma}{\Gamma \vdash x : \tau}\]
\[\frac{\Gamma, \class{hl-new}{\bbox[yellow,1pt]{x{:}\tau_1}} \vdash e : \tau_2}{\Gamma \vdash \lambda x{:}\tau_1.\, e : \tau_1 \to \tau_2}\]
\[\frac{\Gamma \vdash e_1 : \tau_1 \to \tau_2 \quad \Gamma \vdash e_2 : \tau_1}{\Gamma \vdash e_1\, e_2 : \tau_2}\]
\[\frac{\Gamma \vdash e_1 : \mathsf{int} \quad \Gamma \vdash e_2 : \mathsf{int}}{\Gamma \vdash e_1 + e_2 : \mathsf{int}}\]
\[\frac{\Gamma \vdash e : \mathsf{bool} \quad \Gamma \vdash e_1 : \tau \quad \Gamma \vdash e_2 : \tau}{\Gamma \vdash \mathsf{if}\ e\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2 : \tau}\]

The \(\lambda\) rule is the only one that changes the context: to check the body it adds the highlighted \(\class{hl-new}{\bbox[yellow,1pt]{x{:}\tau_1}}\). Every other rule passes \(\Gamma\) along unchanged.

\(\vdash e : \tau\) means \(\cdot \vdash e : \tau\): \(e\) has type \(\tau\) with no variables in scope, so \(e\) is closed.

Examples

A derivation:

\[ \dfrac{\dfrac{\dfrac{x{:}\mathsf{int} \in x{:}\mathsf{int}}{x{:}\mathsf{int} \vdash x : \mathsf{int}} \qquad \dfrac{}{x{:}\mathsf{int} \vdash 1 : \mathsf{int}}}{x{:}\mathsf{int} \vdash x + 1 : \mathsf{int}}}{\vdash \lambda x{:}\mathsf{int}.\, x + 1 : \mathsf{int} \to \mathsf{int}} \]

A non-example: the stuck term \(\mathsf{true} + 1\) from section 2 has no type. The \(+\) rule needs \(\vdash \mathsf{true} : \mathsf{int}\), and the only rule for \(\mathsf{true}\) gives \(\mathsf{bool}\).

4. Type soundness

What does the type system buy us? Section 2 ended with a run that gets stuck: \((\lambda x{:}\mathsf{int}.\, x + 1)\, \mathsf{true} \longrightarrow \mathsf{true} + 1\). Evaluation never looks at types, so nothing stops it. Section 3 showed that \(\mathsf{true} + 1\) has no type. Type soundness says this is no accident: no well-typed program ever reaches a stuck expression. In Milner's slogan, well-typed programs cannot "go wrong" (Milner 1978).

Not stuck, and safe

The lecture's notion is not stuck: \(e\) is a value, or it steps.

\[ \mathsf{not\ stuck}(e) \;:\Longleftrightarrow\; e \text{ is a value} \;\text{ or }\; e \longrightarrow e' \text{ for some } e' \]

An expression is safe when everything it can reach is not stuck:

\[ \mathsf{safe}(e) \;:\Longleftrightarrow\; \mathsf{not\ stuck}(e') \text{ for every } e' \text{ with } e \longrightarrow^* e' \]

The theorem

Type soundness. If \(\vdash e : \tau\), then \(\mathsf{safe}(e)\).

This is the lecture's statement with \(\mathsf{safe}\) unfolded: if \(\vdash e : \tau\) and \(e \longrightarrow^* e'\), then \(e'\) is not stuck, that is, it is a value or it steps.

Are there safe programs that are not well-typed?

Yes. Soundness says the well-typed expressions sit inside the safe ones. The other direction fails: \(\mathsf{if}\ \mathsf{true}\ \mathsf{then}\ 1\ \mathsf{else}\ \mathsf{true} + 1\) always evaluates to \(1\), so it is safe, but it has no type, because its else branch \(\mathsf{true} + 1\) has none. The type system is conservative: it rejects some safe programs so that it never accepts an unsafe one.

A research field. Choosing what "going wrong" means, designing a type system that rules it out, and proving a soundness theorem for it is a large part of programming languages research. A few examples, each ruling out a different kind of bad behavior:

  • Refinement types attach logical conditions to types, such as \(\{ n : \mathsf{int} \mid n > 0 \}\), to rule out errors like division by zero or out-of-bounds array access (Freeman and Pfenning 1991; Rondon, Kawaguchi and Jhala 2008).
  • Linear types require a value to be used exactly once, which rules out using a resource after it is freed or closing a file twice (Girard 1987; Wadler 1990). Rust's ownership types are a close relative (Jung et al. 2018).
  • Graded modal types annotate types with a grade saying how a value may be used: how many times, at what privacy level, with which effects (Brunel et al. 2014; Orchard, Liepelt and Eades 2019).
  • Security typing labels data as public or secret and rules out secret inputs influencing public outputs. Its soundness theorem is called noninterference (Volpano, Smith and Irvine 1996; Sabelfeld and Myers 2003).
  • Session types describe communication protocols, ruling out a program that sends the wrong message at the wrong time (Honda 1993; Honda, Vasconcelos and Kubo 1998).
  • Implicit computational complexity designs type systems whose well-typed programs are exactly the ones in a complexity class, ruling out programs that run too long. For example, Girard's light linear logic (Girard 1998) and Lafont's soft linear logic (Lafont 2004) capture polynomial time, elementary linear logic (Girard 1998) captures elementary time, and Hofmann's safe linear recursion (Hofmann 1997) and non-size-increasing types, LFPL (Hofmann 1999), capture polynomial time in a typed λ-calculus, building on Bellantoni and Cook's safe recursion (1992). Here the soundness theorem reads: every well-typed program runs within the bound.
  • Dependent type theory lets types mention values. Read through the Curry–Howard correspondence, a type is a proposition and a program of that type is a proof, so type checking is proof checking (Howard 1980; Martin-Löf 1984). What it rules out is a "proof" that isn't one: every program must terminate, since a program that runs forever could have any type, even \(\mathsf{False}\). Its soundness theorem is consistency: there is no closed proof of \(\mathsf{False}\). Rocq is one, based on the calculus of constructions (Coquand and Huet 1988), and every Qed on this page is Rocq's type checker checking a proof.
What these type systems look like

For each one: the shape of the judgment, one rule that does the characteristic work, and a small example. The notation is simplified from the papers.

Refinement types. Types carry a logical condition: \(\{ n : \mathsf{int} \mid \varphi \}\) is the integers satisfying \(\varphi\). The key rule weakens the condition when a logic solver proves the implication:

\[\frac{\Gamma \vdash e : \{ n : \mathsf{int} \mid \varphi \} \quad \Gamma \models \varphi \Rightarrow \psi}{\Gamma \vdash e : \{ n : \mathsf{int} \mid \psi \}}\]

Example: with \(\mathsf{div} : \mathsf{int} \to \{ n : \mathsf{int} \mid n \neq 0 \} \to \mathsf{int}\), the call \(\mathsf{div}\ 10\ 0\) is rejected: \(0\) has type \(\{ n : \mathsf{int} \mid n = 0 \}\), and \(n = 0 \Rightarrow n \neq 0\) is false. \(\mathsf{div}\ 10\ 5\) is accepted.

Linear types. Every variable in the context must be used exactly once, so contexts are split between premises instead of shared:

\[\frac{}{x{:}\tau \vdash x : \tau}\]
\[\frac{\Gamma_1 \vdash e_1 : \tau_1 \multimap \tau_2 \quad \Gamma_2 \vdash e_2 : \tau_1}{\Gamma_1, \Gamma_2 \vdash e_1\, e_2 : \tau_2}\]

Example: \(\lambda f{:}\mathsf{file}.\ \mathsf{close}\ f\) is accepted, but \(\lambda f{:}\mathsf{file}.\ (\mathsf{close}\ f;\ \mathsf{close}\ f)\) is rejected: \(f\) would have to go to both halves of the context split, and it can go to only one.

Graded modal types. Each variable carries a grade \(r\) saying how it may be used, here a count:

\[ x :_{r} \tau \;\vdash\; e : \tau' \]

Example: \(x :_{2} \mathsf{int} \vdash x + x : \mathsf{int}\), because \(x\) is used twice, so \(\lambda x.\, x + x\) gets a type saying it uses its argument twice. With grades from a different set, such as privacy levels, the same machinery tracks who may see a value.

Security typing. Types carry a level, \(\mathsf{int}_L\) (public) or \(\mathsf{int}_H\) (secret), and information may only flow upward, \(L \sqsubseteq H\):

\[\frac{\Gamma \vdash e : \mathsf{int}_{\ell} \quad \ell \sqsubseteq \ell'}{\Gamma \vdash e : \mathsf{int}_{\ell'}}\]

Example: with \(h : \mathsf{int}_H\) and \(l : \mathsf{int}_L\), the assignment \(l := h\) is rejected, and so is \(\mathsf{if}\ h > 0\ \mathsf{then}\ l := 1\ \mathsf{else}\ l := 0\): the branch taken reveals something about \(h\), so code under a secret test may only write secret variables. Noninterference then says changing \(h\) never changes what \(l\) ends up holding.

Session types. A channel's type is the protocol it follows: \(!\mathsf{int}.\,?\mathsf{bool}.\,\mathsf{end}\) means send an int, then receive a Boolean, then stop. The two ends of a channel get dual types, with sends and receives swapped:

\[ c : !\mathsf{int}.\,?\mathsf{bool}.\,\mathsf{end} \qquad\qquad \overline{c} : ?\mathsf{int}.\,!\mathsf{bool}.\,\mathsf{end} \]

Example: a client that runs \(\mathsf{send}\ c\ 5\) and then \(\mathsf{recv}\ c\) is accepted. One that receives first is rejected, because it doesn't follow the protocol and would wait forever for the server.

Implicit computational complexity. Three examples, for two complexity classes.

Polynomial time, by safe recursion (Bellantoni and Cook 1992). A function's arguments are split into normal ones, written before a semicolon, which recursion may go down, and safe ones, after it, which may only be passed along or extended by a constructor. A recursive call's result may only be used in a safe position:

\[ \begin{aligned} \mathsf{add}(0;\, y) &= y & \mathsf{add}(x{+}1;\, y) &= \mathsf{add}(x;\, y) + 1 \\ \mathsf{mul}(0, y;\,) &= 0 & \mathsf{mul}(x{+}1, y;\,) &= \mathsf{add}(y;\, \mathsf{mul}(x, y;\,)) \end{aligned} \]

Both are accepted: in \(\mathsf{mul}\), the recursive result goes into \(\mathsf{add}\)'s safe slot. Exponentiation is rejected: \(\mathsf{exp}(x{+}1;\,) = \mathsf{add}(\mathsf{exp}(x;\,);\, \mathsf{exp}(x;\,))\) would put a recursive result into a normal slot, where it could be recursed on again, and that is how running time blows up.

Polynomial time, by counting cells. In Hofmann's LFPL, building a list cell costs a token of a special type \(\diamond\), and tokens are linear:

\[ \mathsf{cons} : \diamond \multimap \tau \multimap \mathsf{list}\ \tau \multimap \mathsf{list}\ \tau \]

A list comes with one token per cell, so a function can never output more cells than it was given. Example: reversing a list is accepted, since it reuses each cell's token. Doubling a list, which builds two cells for each one, is rejected, because there aren't enough tokens. Without that growth, iteration stays within polynomial time.

Logarithmic space, by not building data (Jones 1999). A cons-free program may look at its input and walk over it, but it may never build new data: no list cells, no new numbers beyond a fixed set. First-order cons-free programs compute exactly the problems in logarithmic space: all they can remember is a fixed number of positions in the input, and a position takes \(\log n\) bits. Example: checking whether a list has even length, by walking down it and flipping a Boolean, is cons-free. Reversing a list is not, because it builds a new list. Allowing general recursion in the same programs gives exactly polynomial time instead.

Dependent type theory. In a dependent function type \(\Pi x{:}A.\, B\), the result type \(B\) may mention the argument \(x\):

\[\frac{\Gamma, x{:}A \vdash e : B}{\Gamma \vdash \lambda x{:}A.\, e : \Pi x{:}A.\, B}\]

A statement like "every \(n\) satisfies \(n + 0 = n\)" is the type \(\Pi n{:}\mathsf{nat}.\, n + 0 = n\), and a proof of it is a function that, given \(n\), returns evidence that \(n + 0 = n\). In Rocq, forall n : nat, n + 0 = n is that type, and the proof script after Proof. builds such a function, which the type checker then checks. The termination requirement shows up as a rejected definition: Fixpoint loop (n : nat) : False := loop n. would prove \(\mathsf{False}\) by running forever, so Rocq refuses it, because the recursive call is not on a smaller argument.

Each comes with its own version of the theorem we prove here: well-typed programs don't do the bad thing.

The theorem talks about whole runs, which can be any length. The standard way to prove it (Wright and Felleisen 1994) is to split it into two facts about a single step:

Progress. If \(\vdash e : \tau\), then \(\mathsf{not\ stuck}(e)\). Unfolded, this is the lecture's statement: \(e\) is a value or \(e \longrightarrow e'\) for some \(e'\).

Preservation. If \(\vdash e : \tau\) and \(e \longrightarrow e'\), then \(\vdash e' : \tau\).

Progress says a well-typed expression is not stuck right now. Preservation says a step keeps the type, so after the step the expression is still well-typed, and progress applies again. Neither one alone is enough: progress says nothing about the future, and preservation alone allows a well-typed expression that is stuck.

Proving soundness. We want to prove \(\vdash e : \tau \implies \mathsf{safe}(e)\). Unfolding \(\mathsf{safe}\), it suffices to show: given \(\vdash e : \tau\) and \(e \longrightarrow^* e'\), that \(e'\) is not stuck.

We induct on the run \(e \longrightarrow^* e'\), one case for each rule. What the induction proves is "if the start of the run has type \(\tau\), then its end is not stuck", so the induction hypothesis is about the shorter run and its own start.

  • Case (refl): the run takes no steps, so \(e' = e\).
    Assumptions: \(\vdash e : \tau\).
    Goal: \(\mathsf{not\ stuck}(e)\).
    Progress gives it directly.
  • Case (step): the run is a first step \(e \longrightarrow e''\), then the rest \(e'' \longrightarrow^* e'\).
    Assumptions: \(\vdash e : \tau\); \(e \longrightarrow e''\); \(e'' \longrightarrow^* e'\); and the induction hypothesis for the shorter run, if \(\vdash e'' : \tau\) then \(\mathsf{not\ stuck}(e')\).
    Goal: \(\mathsf{not\ stuck}(e')\).
    Preservation, from \(\vdash e : \tau\) and \(e \longrightarrow e''\), gives \(\vdash e'' : \tau\). The induction hypothesis then gives \(\mathsf{not\ stuck}(e')\).

So everything comes down to progress and preservation. We first prove soundness assuming them, and then prove each one. In Rocq the assumptions are Hypothesis declarations inside a Section. When the section ends, soundness becomes a theorem that takes progress and preservation as arguments, so the assumptions stay visible in its type.

Canonical forms

Canonical forms. For a value \(v\):

  • if \(\vdash v : \mathsf{int}\), then \(v\) is a number;
  • if \(\vdash v : \mathsf{bool}\), then \(v\) is \(\mathsf{true}\) or \(\mathsf{false}\);
  • if \(\vdash v : \tau_1 \to \tau_2\), then \(v\) is \(\lambda x{:}\tau_1.\, e\) for some \(x\) and \(e\).

Proof. Go through the four kinds of value. For each wrong pairing, such as a \(\lambda\) at type \(\mathsf{int}\), no typing rule gives that type.

Steps inside a context (congruence)

Steps inside a context (congruence). If \(e \longrightarrow e'\), then \(E[e] \longrightarrow E[e']\) for any evaluation context \(E\).

Proof. The step \(e \longrightarrow e'\) is \(E'[r] \longrightarrow E'[r']\) for some context \(E'\) and redex \(r\). Putting \(E'\) into the hole of \(E\) gives one bigger context, and \(E[E'[r]] \longrightarrow E[E'[r']]\) is the step rule with that context.

In Rocq, compose E E' is that bigger context, and plug_compose says plugging into it is plugging twice: \((\mathsf{compose}\ E\ E')[e] = E[E'[e]]\).

Progress

Progress. If \(\vdash e : \tau\), then \(\mathsf{not\ stuck}(e)\).

The typing rules, for reference
\[\frac{}{\Gamma \vdash n : \mathsf{int}}\]
\[\frac{}{\Gamma \vdash \mathsf{true} : \mathsf{bool}}\]
\[\frac{}{\Gamma \vdash \mathsf{false} : \mathsf{bool}}\]
\[\frac{x{:}\tau \in \Gamma}{\Gamma \vdash x : \tau}\]
\[\frac{\Gamma, \class{hl-new}{\bbox[yellow,1pt]{x{:}\tau_1}} \vdash e : \tau_2}{\Gamma \vdash \lambda x{:}\tau_1.\, e : \tau_1 \to \tau_2}\]
\[\frac{\Gamma \vdash e_1 : \tau_1 \to \tau_2 \quad \Gamma \vdash e_2 : \tau_1}{\Gamma \vdash e_1\, e_2 : \tau_2}\]
\[\frac{\Gamma \vdash e_1 : \mathsf{int} \quad \Gamma \vdash e_2 : \mathsf{int}}{\Gamma \vdash e_1 + e_2 : \mathsf{int}}\]
\[\frac{\Gamma \vdash e : \mathsf{bool} \quad \Gamma \vdash e_1 : \tau \quad \Gamma \vdash e_2 : \tau}{\Gamma \vdash \mathsf{if}\ e\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2 : \tau}\]

The idea. We go through the typing rules one at a time.

  • A variable \(x\) is impossible: there is nothing in scope.
  • \(n\), \(\mathsf{true}\), \(\mathsf{false}\) and \(\lambda x{:}\tau_1.\, e\) are values, so they are not stuck.
  • Applications, sums and ifs are never values, so we have to show that they step. How? By the induction hypothesis every subterm is not stuck: it is a value, or it steps to something.

For example, take an application \(e_1\, e_2\). The induction hypotheses say \(\mathsf{not\ stuck}(e_1)\) and \(\mathsf{not\ stuck}(e_2)\), so we work by cases:

  • If \(e_1\) steps, the whole application steps, by a congruence: the step happens inside the context \(\bullet\, e_2\).
  • If \(e_1\) is a value, then it must be a \(\lambda\): its type is a function type, so canonical forms says so. Now consider \(e_2\):
    • if \(e_2\) is a value, we perform the substitution: \(e_1\, e_2\) is a β-redex;
    • otherwise \(e_2\) steps, so we do a congruence, inside the context \(e_1\, \bullet\).

Proof. By induction on the derivation of \(\vdash e : \tau\), one case per typing rule. The variable, value and application cases are as above.

  • \(e_1 + e_2\): similar to application. If \(e_1\) steps, do a congruence inside \(\bullet + e_2\). If \(e_1\) is a value, canonical forms makes it a number \(n_1\), since its type is \(\mathsf{int}\). Then if \(e_2\) steps, do a congruence inside \(n_1 + \bullet\); if \(e_2\) is a value, it is a number \(n_2\) too, and \(n_1 + n_2\) is a redex.
  • \(\mathsf{if}\ e\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2\): similar, with only the condition to look at. If it steps, do a congruence inside \(\mathsf{if}\ \bullet\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2\). If it is a value, canonical forms makes it \(\mathsf{true}\) or \(\mathsf{false}\), and an if rule applies.

Canonical forms is what turns "a value of the right type" into "the shape a redex rule needs".

Weakening

Write \(\Gamma \subseteq \Gamma'\) for: every \(x{:}\tau \in \Gamma\) is also \(x{:}\tau \in \Gamma'\).

Weakening. If \(\Gamma \subseteq \Gamma'\) and \(\Gamma \vdash e : \tau\), then \(\Gamma' \vdash e : \tau\).

Proof idea. By induction on the derivation of \(\Gamma \vdash e : \tau\). The induction hypothesis is about each premise of the last rule: if the premise is \(\Gamma_0 \vdash e_0 : \tau_0\), then \(\Gamma_0' \vdash e_0 : \tau_0\) for every \(\Gamma_0'\) with \(\Gamma_0 \subseteq \Gamma_0'\). It has to cover every bigger context, because the \(\lambda\) case uses it with \(\Gamma, x{:}\tau_1\).

  • Cases \(n\), \(\mathsf{true}\), \(\mathsf{false}\): these rules have no premises, so there is no induction hypothesis, and they never look at the context, so the same rule gives the type in \(\Gamma'\).
  • Case \(x\): the premise is \(x{:}\tau \in \Gamma\), a lookup rather than a typing, so again no induction hypothesis. Since \(\Gamma \subseteq \Gamma'\), also \(x{:}\tau \in \Gamma'\), and the variable rule gives \(\Gamma' \vdash x : \tau\).
  • Case \(\lambda x{:}\tau_1.\, e\): the premise checks the body in a bigger context, \(\Gamma, x{:}\tau_1 \vdash e : \tau_2\). Both contexts get the same \(x{:}\tau_1\) added, so \(\Gamma, x{:}\tau_1 \subseteq \Gamma', x{:}\tau_1\): looking up \(x\), both find \(x{:}\tau_1\) at the front; looking up any other variable, both look further, in \(\Gamma\) and \(\Gamma'\). The induction hypothesis gives \(\Gamma', x{:}\tau_1 \vdash e : \tau_2\), and the \(\lambda\) rule gives \(\Gamma' \vdash \lambda x{:}\tau_1.\, e : \tau_1 \to \tau_2\).
  • Cases application, \(+\), \(\mathsf{if}\): these rules pass the same context to every premise. Use the induction hypothesis on each premise to move it to \(\Gamma'\), then apply the same rule.

The substitution lemma

On paper (TAPL §9.3), the substitution lemma is:

Substitution lemma, on paper. If \(\Gamma, x{:}\sigma \vdash e : \tau\) and \(\Gamma \vdash v : \sigma\), then \(\Gamma \vdash e[x \mapsto v] : \tau\).

There \(v\) may use the variables of \(\Gamma\), and \(e[x \mapsto v]\) is capture-avoiding: bound variables are renamed so that no free variable of \(v\) gets captured. In the \(\lambda\) case one renames \(\lambda y\) so that \(y \ne x\) and \(y\) is not free in \(v\), and then pushes the substitution inside; reordering and hiding entries of the context are left implicit.

Substitution lemma, ours. If \(\Gamma, x{:}\sigma \vdash e : \tau\) and \(\vdash v : \sigma\), then \(\Gamma \vdash e[x \mapsto v] : \tau\).

The only change is that \(v\) is typed in the empty context, so \(v\) is closed. Our substitution never renames, which is fine because nothing in a closed \(v\) can be captured. And it is all preservation needs: evaluation never looks inside a \(\lambda\), so in a closed program the argument of every β step is closed. In return, the proof does by hand the context bookkeeping that the paper proof leaves implicit.

Proof idea. By induction on the expression \(e\). The induction hypothesis is about each immediate subexpression \(e_0\) of \(e\): for every \(\Gamma\) and \(\tau\), if \(\Gamma, x{:}\sigma \vdash e_0 : \tau\) then \(\Gamma \vdash e_0[x \mapsto v] : \tau\). It has to cover every \(\Gamma\), because the \(\lambda\) case uses it with \(\Gamma, y{:}\tau_y\). The assumption \(\vdash v : \sigma\) is used only in the case \(y = x\).

  • Cases \(n\), \(\mathsf{true}\), \(\mathsf{false}\): no subexpressions, so no induction hypothesis. Substitution does nothing, and these rules never look at the context, so the same rule gives the type in \(\Gamma\).
  • Case \(y\): no subexpressions, so no induction hypothesis. Two cases.
    • \(y = x\): the premise is \(x{:}\tau \in \Gamma, x{:}\sigma\), so \(\tau = \sigma\), and \(e[x \mapsto v] = v\). We have \(\vdash v : \sigma\) in the empty context; weakening moves it to \(\Gamma\).
    • \(y \ne x\): \(e[x \mapsto v] = y\), and \(y{:}\tau \in \Gamma, x{:}\sigma\) with \(y \ne x\) means \(y{:}\tau \in \Gamma\). The variable rule gives \(\Gamma \vdash y : \tau\).
  • Case \(\lambda y{:}\tau_y.\, e_0\): here \(\tau = \tau_y \to \tau_2\), and the body is checked as \(\Gamma, x{:}\sigma, y{:}\tau_y \vdash e_0 : \tau_2\). Two cases.
    • \(y = x\): substitution stops, so \(e[x \mapsto v] = e\), and the induction hypothesis isn't needed. The inner \(x{:}\tau_y\) hides the outer \(x{:}\sigma\), so \(\Gamma, x{:}\sigma, x{:}\tau_y \subseteq \Gamma, x{:}\tau_y\). Weakening moves the body's typing there, and the \(\lambda\) rule gives the type in \(\Gamma\).
    • \(y \ne x\): \(e[x \mapsto v] = \lambda y{:}\tau_y.\, e_0[x \mapsto v]\). Since \(y \ne x\), the order of the two entries doesn't matter, so weakening reorders \(\Gamma, x{:}\sigma, y{:}\tau_y\) to \(\Gamma, y{:}\tau_y, x{:}\sigma\). Now the induction hypothesis, with \(\Gamma, y{:}\tau_y\) in place of \(\Gamma\), gives \(\Gamma, y{:}\tau_y \vdash e_0[x \mapsto v] : \tau_2\), and the \(\lambda\) rule finishes.
  • Cases application, \(+\), \(\mathsf{if}\): substitution goes into each piece, and these rules pass the same context to every premise. Use the induction hypothesis on each premise, then apply the same rule.

Redex preservation

Redex preservation. If \(\vdash e : \tau\) and \(e \longrightarrow_{\mathsf{r}} e'\), then \(\vdash e' : \tau\).

Only β needs real work, and that is the substitution lemma.

Proof idea. No induction: just one case per redex rule, so there is no induction hypothesis. In each case, read the types of the pieces off the typing derivation of the left side: its last rule is the typing rule for that form of expression. The substitution lemma is used only in the β case.

  • Case β: \((\lambda x{:}\sigma.\, e_0)\, v \longrightarrow_{\mathsf{r}} e_0[x \mapsto v]\).
    • The last rule of \(\vdash (\lambda x{:}\sigma.\, e_0)\, v : \tau\) is the application rule, so \(\vdash \lambda x{:}\sigma.\, e_0 : \sigma \to \tau\) and \(\vdash v : \sigma\).
    • The last rule of \(\vdash \lambda x{:}\sigma.\, e_0 : \sigma \to \tau\) is the \(\lambda\) rule, so \(x{:}\sigma \vdash e_0 : \tau\).
    • The substitution lemma, with \(\Gamma\) empty, gives \(\vdash e_0[x \mapsto v] : \tau\).
  • Case \(n_1 + n_2 \longrightarrow_{\mathsf{r}} n_3\): the \(+\) rule gives the sum type \(\mathsf{int}\), and the number \(n_3\) has type \(\mathsf{int}\) too.
  • Cases \(\mathsf{if}\ \mathsf{true}\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2 \longrightarrow_{\mathsf{r}} e_1\) and \(\mathsf{if}\ \mathsf{false}\ \mathsf{then}\ e_1\ \mathsf{else}\ e_2 \longrightarrow_{\mathsf{r}} e_2\): the if rule needs both branches at type \(\tau\), so the branch we step to has type \(\tau\).
