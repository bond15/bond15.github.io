    1. Core combinators and fixed points

    ID := λx.x

Y := λf.(λx.f(xx))(λx.f(xx))

OMEGA := Y ID

    2. Church booleans

    TRUE := λx.λy.x
FALSE := λx.λy.y

ITE := λb.λt.λf.btf

NOT := λm.m FALSE TRUE
OR := λm.λn.m TRUE n
AND := λm.λn.mn FALSE

NOR := λa.λb.NOT (OR a b)
NAND := λa.λb.NOT (AND a b)
XOR := λm.λn.AND (OR m n) (NAND m n)

    3. Church numerals

    Let us start by writing the first few numerals directly.

    ZERO := λf.λx.x
ONE := λf.λx.fx
TWO := λf.λx.f(fx)

    A Church numeral represents a natural number by iteration:

    ZERO f x --> x
ONE  f x --> fx
TWO  f x --> f(fx)

    So rather than thinking “where is the integer 2 stored?”, think:

    TWO is a program that knows how to apply a step function twice.

    At this point, though, writing numerals by hand is already getting annoying. To write THREE, we would add one more f; for FOUR, one more again; and so on.

    Instead,

    SUCC := λn.λf.λx.f(nfx)

    Read this from the inside out. n f x applies f exactly n times, and then the outer f applies it one more time. So if n represents a number, SUCC n represents its successor.

    For example:

    SUCC TWO f x
--> f(TWO f x)
--> f(f(fx))

    Now we no longer need to manually write larger numerals:

    THREE := SUCC TWO
FOUR := SUCC THREE
FIVE := SUCC FOUR

    4. Arithmetic on Church numerals

    Now that SUCC is available, we can use a Church numeral's iteration behavior to build arithmetic almost mechanically.

    ADD := λn.λm.n SUCC m
MULT := λa.λb.b (ADD a) ZERO
EXP := λa.λb.b (MULT a) ONE

    The key is to read these definitions in terms of iteration.

    ADD n m means:

    start at m, and apply SUCC exactly n times.

    So:

    ADD TWO THREE

    means “start at three and take two successor steps.”

    MULT a b means:

    start at zero and add a, b times.

    EXP a b means:

    start at one and multiply by a, b times.

    This is a nice example of building a tower of abstractions: once we have iteration and successor, addition becomes easy; once we have addition, multiplication becomes easy; once we have multiplication, exponentiation becomes easy.

    5. Pairs

    PAIR := λa.λb.λf.fab
FIRST := λp.p TRUE
SECOND := λp.p FALSE

    A pair is represented by what you can do with its two components.

    PAIR A B f --> f A B

    The pair waits for a consumer f, then hands both components to it.

    The projections are just carefully chosen consumers:

    • TRUE chooses the first argument.
    • FALSE chooses the second argument.

    So:

    FIRST  (PAIR A B) --> A
SECOND (PAIR A B) --> B

    6. Predicates and predecessor

    ISZERO := λn.n (λx.FALSE) TRUE

PRED := λn.FIRST (n (λp.PAIR (SECOND p) (SUCC (SECOND p))) (PAIR ZERO ZERO))

LT := λm.λn.NOT (ISZERO (m PRED n))

EQ := λm.λn.AND (ISZERO (m PRED n)) (ISZERO (n PRED m))

    ISZERO uses the fact that a Church numeral tells us how many iterations happened.

    Start from TRUE. Every iteration replaces the current result with FALSE.

    So:

    ISZERO ZERO --> TRUE

    because no iteration happens, while any nonzero numeral performs at least one step and produces FALSE.

    PRED is more interesting. A Church numeral only gives us the final result of an iteration; it does not directly expose “the previous iteration.” So we carry extra state in a pair.

    The pair evolves so that it remembers two neighboring values. After enough iterations, the first component is the predecessor we want.

    This is a good example of a more general programming trick:

    if an iteration does not expose enough information, enrich the accumulator with extra state.

    7. Recursive numeric examples

    Factorial

    FACTSTEP := λf.λn.ITE (ISZERO n) ONE (MULT n (f (PRED n)))
FACT := Y FACTSTEP

    FACTSTEP is deliberately not recursive by itself. It receives a parameter f that stands for “the recursive call.”

    If someone handed us the correct recursive factorial function as f, then FACTSTEP f would know how to compute one layer:

    • at zero, return ONE;
    • otherwise multiply n by f (PRED n).

    Y ties the knot by supplying the self-reference.

    Example:

    FACT TWO

    reduces to TWO.

    8. Scott-encoded lists

    Start from the ordinary inductive datatype:

    List A ::= Nil | Cons A (List A)

    How to derive the Scott encoding

    A list has exactly two constructors, so a Scott-encoded list takes exactly two arguments describing what to do in each case:

    1. what to do in the Nil case;
    2. what to do in the Cons h t case.

    Call these two case arguments n and c.

    Now encode each constructor by choosing the corresponding case.

    Nil has no fields, so it simply chooses the Nil case:

    NIL := λn.λc.n

    Cons has two fields, the head h and tail t, so it chooses the Cons case and supplies those two fields:

    CONS := λh.λt.λn.λc.cht

    That means a Scott list is already a one-step pattern match.

    For an arbitrary encoded list l:

    l nilCase consCase

    behaves like:

    match l with
| Nil      -> nilCase
| Cons h t -> consCase h t

    The crucial Scott-encoding idea is:

    the stored value chooses the constructor case, and exposes that constructor's fields.

    This is different from the Church-list viewpoint. Scott encoding makes pattern matching easy; recursion still has to be supplied separately.

    Destructors

    Because a Scott list exposes the head and tail immediately in the Cons case, HEAD and TAIL are short:

    HEAD := λl.l ID (λh.λt.h)
TAIL := λl.l NIL (λh.λt.t)

    The important thing to remember is that a Scott list acts like a tiny case distinction. If we write

    l nilCase consCase

    then l decides whether it is NIL or CONS. A NIL returns the first argument. A CONS h t calls the second argument and gives it the stored head h and tail t.

    How HEAD works

    Read

    HEAD := λl.l ID (λh.λt.h)

    as:

    • if the list is NIL, return ID;
    • if the list is CONS h t, return h.

    The Cons case is the function

    λh.λt.h

    which receives both pieces stored in the list and simply selects the first one.

    For example, suppose the list is CONS a r. Then:

    HEAD (CONS a r)
--> (CONS a r) ID (λh.λt.h)
--> (λh.λt.h) a r
--> a

    Expanding CONS one more step makes the mechanism completely explicit:

    CONS a r
= (λh.λt.λn.λc.c h t) a r
--> λn.λc.c a r

    so applying this encoded list to the two cases gives

    (λn.λc.c a r) ID (λh.λt.h)
--> (λh.λt.h) a r
--> a

    For the empty list:

    HEAD NIL
--> NIL ID (λh.λt.h)
--> ID

    There is no genuine head of an empty list. ID is just the arbitrary default value we chose for that case.

    How TAIL works

    Similarly,

    TAIL := λl.l NIL (λh.λt.t)

    means:

    • if the list is NIL, return NIL;
    • if the list is CONS h t, return t.

    Now the Cons case is

    λh.λt.t

    which receives both stored pieces and selects the second one. Therefore:

    TAIL (CONS a r)
--> (CONS a r) NIL (λh.λt.t)
--> (λh.λt.t) a r
--> r

    and

    TAIL NIL
--> NIL NIL (λh.λt.t)
--> NIL

    So HEAD and TAIL have exactly the same overall shape. The difference is just which component the Cons case selects:

    λh.λt.h    # choose the head
λh.λt.t    # choose the tail

    Recursive fold

    To traverse the whole Scott list, we add recursion explicitly:

    FOLD := Y (λg.λf.λz.λx.x z (λh.λt.f h (g f z t)))

    The intended equations are:

    FOLD f z NIL        --> z
FOLD f z (CONS h t) --> f h (FOLD f z t)

    This is a useful distinction to emphasize:

    • Scott encoding gives us one layer of case analysis for free.
    • Y gives us recursive traversal.

    Example list

    X := CONS TWO (CONS THREE (CONS ONE NIL))

    This is the list [2,3,1].

    Indexing into a Scott list

    We will use environments later, so define:

    NTH := λn.λr.HEAD (n TAIL r)

    A Church numeral n iterates TAIL n times, then HEAD takes the first remaining element.

    So:

    NTH ZERO r

    returns the first element of r, while:

    NTH ONE r

    returns the second.

    9. Scott-encoded binary search trees

    Start with:

    Tree ::= Empty | Node Nat Tree Tree

    Again there are exactly two constructors, so a Scott-encoded tree takes two arguments describing the two cases:

    • what to do for Empty;
    • what to do for Node.

    Empty has no fields, so it chooses the first case:

    EMPTY := λe.λn.e

    Node has three fields — key, left subtree, and right subtree — so it chooses the second case and supplies all three:

    NODE := λk.λl.λr.λe.λn.nklr

    For any encoded tree t:

    t emptyCase nodeCase

    acts like:

    match t with
| Empty          -> emptyCase
| Node k left right -> nodeCase k left right

    This is exactly the same Scott recipe as lists. Only the number of fields in the nonempty constructor changed.

    LEAF is an alias for EMPTY in this representation:

    LEAF := EMPTY

    Example BST:

    TREE := NODE TWO (NODE ONE EMPTY EMPTY) (NODE THREE EMPTY EMPTY)

    Binary search

    SEARCH :=
  Y (λs.λx.λt.
    t
      FALSE
      (λk.λl.λr.
        ITE (EQ x k)
            TRUE
            (ITE (LT x k)
                 (s x l)
                 (s x r))))

    Read the body structurally:

    • pattern match on t;
    • Empty means failure, so return FALSE;
    • Node k l r exposes the three fields;
    • if x = k, return TRUE;
    • if x < k, recursively search l;
    • otherwise recursively search r.

    Call it as:

    SEARCH TWO TREE
SEARCH FOUR TREE

    The first reduces to TRUE; the second reduces to FALSE.

    10. A minimal UTLC interpreter written in UTLC

    Now we do something more self-referential: use UTLC to represent the syntax of UTLC itself as data, and then write an evaluator for that representation.

    The object language is:

    t ::= Var n | Lam t | App t t

    We use de Bruijn indices for variables:

    • ZERO means “the variable bound by the nearest enclosing lambda”;
    • ONE means “skip one binder and use the next one”;
    • and so on.

    Step 1: Scott-encode the syntax tree

    There are exactly three constructors, so every encoded syntax tree takes exactly three functions telling it what to do in each constructor case:

    1. what to do for Var;
    2. what to do for Lam;
    3. what to do for App.

    Call these three case functions v, l, and a.

    Now follow the Scott recipe locally.

    Var i chooses the Var case and supplies its index:

    UVAR := λi.λv.λl.λa.vi

    Lam b chooses the Lam case and supplies its body:

    ULAM := λb.λv.λl.λa.lb

    App f x chooses the App case and supplies both subterms:

    UAPP := λf.λx.λv.λl.λa.afx

    So the following are the pattern-matching equations:

    UVAR i  v l a --> v i
ULAM b   v l a --> l b
UAPP f x v l a --> a f x

    This is the key thing to understand before looking at the evaluator:

    An encoded UTLC term is a syntax tree that waits for us to tell it what Var, Lam, and App mean.

    The evaluator will provide those three meanings.

    Step 2: Use an environment for variables

    Instead of implementing substitution directly, evaluate terms relative to an environment r.

    The environment is a Scott list of values.

    Because we moved NTH into the list section, we already have:

    NTH := λn.λr.HEAD (n TAIL r)

    So a de Bruijn variable is interpreted by indexing into the environment:

    Var i  ==>  NTH i r

    This is the bridge between de Bruijn syntax and runtime values.

    Step 3: Give meanings to the three constructors

    The evaluator is:

    UEVAL :=
  Y (λe.λt.λr.
    t
      (λi.NTH i r)
      (λb.λx.e b (CONS x r))
      (λf.λx.(e f r)(e x r)))

    There are three nested ideas here.

    The outer parameters

    λe.λt.λr. ...
    • e is the recursive evaluator;
    • t is the encoded syntax tree being evaluated;
    • r is the current environment.

    Then we write:

    t varCase lamCase appCase

    because t is Scott-encoded syntax.

    Variable case

    λi.NTH i r

    If the syntax is Var i, look up the ith value in the current environment.

    Lambda case

    λb.λx.e b (CONS x r)

    If the syntax is Lam b, evaluating it should produce an actual function.

    So we return:

    λx. ...

    When that function eventually receives an argument x, we evaluate the body b in an environment where x has been added to the front.

    This is exactly what de Bruijn index ZERO expects: the newest binder lives at the head of the environment.

    Application case

    λf.λx.(e f r)(e x r)

    If the syntax is App f x, recursively evaluate the function part and the argument part, then apply the resulting function to the resulting argument.

    The reduction strategy of the outer UTLC reducer still determines the precise order in which those computations are reduced; conceptually, this clause gives the semantic meaning of application.

    Two levels of λ-calculus

    This example has two conceptual levels, even though both are represented using the same underlying UTLC syntax.

    Object level: the encoded program:

    UVAR ...
ULAM ...
UAPP ...

    These are data.

    Interpreter level: UEVAL and the λ-terms implementing it.

    These are the program manipulating that data.

    Keeping those levels separate is the main conceptual challenge.

    Encoded identity

    The object-language term

    λx.x

    has body Var 0, so:

    OID := ULAM (UVAR ZERO)

    Run:

    UEVAL OID NIL

    and the result is:

    ID

    Encoded application

    Represent the object-language term:

    (λx.x) (λx.x)

    as:

    OTEST := UAPP (ULAM (UVAR ZERO)) (ULAM (UVAR ZERO))

    Then:

    UEVAL OTEST NIL

    evaluates to ID.

    Encoded diverging term

    We can even represent the usual self-application loop as data:

    OOMEGA :=
  UAPP
    (ULAM (UAPP (UVAR ZERO) (UVAR ZERO)))
    (ULAM (UAPP (UVAR ZERO) (UVAR ZERO)))

    Then:

    UEVAL OOMEGA NIL

    diverges, as the represented object program should.

    11. Evaluating Church numerals and addition with UEVAL

    UEVAL takes an encoded syntax tree and an environment. To evaluate a Church numeral, first represent its lambda expression using ULAM, UAPP, and UVAR.

    All the programs below are closed, so we evaluate them with the empty environment NIL.

    Recall the ordinary Church numerals:

    ZERO := λf.λx.x
ONE := λf.λx.fx
TWO := λf.λx.f(fx)

    Their encoded syntax trees are:

    OZERO := ULAM (ULAM (UVAR ZERO))
OONE := ULAM (ULAM (UAPP (UVAR ONE) (UVAR ZERO)))
OTWO := ULAM (ULAM (UAPP (UVAR ONE) (UAPP (UVAR ONE) (UVAR ZERO))))

    Notice the two uses of numerals: ZERO inside UVAR ZERO is a variable index, while OZERO is the syntax tree of the entire Church numeral zero.

    Run these examples. Here -->* means several beta-reduction steps; bound-variable names may differ.

    UEVAL OZERO NIL -->* λf.λx.x          # ZERO
UEVAL OONE NIL  -->* λf.λx.fx         # ONE
UEVAL OTWO NIL  -->* λf.λx.f(fx)      # TWO

    Encode successor and construct three

    The successor function from earlier is:

    SUCC := λn.λf.λx.f(nfx)

    Inside its body, x has index ZERO, f has index ONE, and n has index TWO. Therefore:

    OSUCC := ULAM (ULAM (ULAM (UAPP (UVAR ONE) (UAPP (UAPP (UVAR TWO) (UVAR ONE)) (UVAR ZERO)))))
OTHREE := UAPP OSUCC OTWO

    OTHREE represents the program SUCC TWO. Evaluating that program computes three:

    UEVAL OTHREE NIL -->* λf.λx.f(f(fx))  # THREE

    We use UAPP OSUCC OTWO to build the syntax of an application. The interpreter then performs that application.

    Encode addition

    Use exactly the addition algorithm defined earlier:

    ADD := λn.λm.n SUCC m

    In this body, m has index ZERO and n has index ONE. We insert the closed syntax tree OSUCC directly as a subexpression:

    OADD := ULAM (ULAM (UAPP (UAPP (UVAR ONE) OSUCC) (UVAR ZERO)))

    Because OSUCC is closed, its variable indices still refer to its own three binders; embedding it under the two lambdas in OADD requires no index changes.

    Now build programs for one plus two and two plus three:

    OADD12 := UAPP (UAPP OADD OONE) OTWO
OADD23 := UAPP (UAPP OADD OTWO) OTHREE

    Each program uses two UAPP constructors because addition receives its arguments one at a time.

    UEVAL OADD12 NIL -->* λf.λx.f(f(fx))        # THREE
UEVAL OADD23 NIL -->* λf.λx.f(f(f(f(fx))))  # FIVE

    You can also build a program directly in the call to UEVAL:

    UEVAL (UAPP (UAPP OADD OZERO) OTWO) NIL -->* λf.λx.f(fx)  # TWO

    Finally, use the earlier equality predicate to check the computed results:

    EQ (UEVAL OADD12 NIL) THREE -->* TRUE
EQ (UEVAL OADD23 NIL) FIVE  -->* TRUE

    In these last two calls, UEVAL evaluates the encoded addition program, and EQ compares the resulting ordinary Church numeral with the expected answer.
